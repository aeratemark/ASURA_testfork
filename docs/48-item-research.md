# Item research from Rurik and cmonmeow

The normalized candidate table is `recordings/client/feature/items/items-rurik-cmonmeow.json`. It is
generated by `tools/extract-item-research.py` from the two checkouts under `Other_Repos_Research/`, and
it is a review table, not the world pack.

## What the table holds

| source | rows | what the rows are |
|---|---|---|
| Rurik `content/items.toml` | 28 | hand-curated item rows with capture or OpenTyria provenance |
| cmonmeow `runtime/*.h` | 62 | captured `items::Definition` literals from pre-Searing collectors, crafters, quests and starters |
| total item candidates | 90 | after exact duplicate rows inside one source are collapsed |
| currencies | 1 | Rurik's gold coin row, kept out of the item candidates |

Gold is not a normal item here. It is the character's gold scalar, and the client displays platinum
as 1000 gold. The extraction keeps the one captured gold row in `currencies` for research only and
does not offer it for the item catalogue.

The item types covered are 2, 3, 4, 5, 7, 10, 12, 13, 15, 16, 19, 21, 22, 24, 26, 27, 28, 29, 30,
32, 35, 36, 44 and 45. The largest groups are foci (20 rows), starter wands (8), trophies (7),
bows (5), shields (5) and staves (5).

## What each source is good for

**Rurik** has the strongest per-row evidence labels. The rows marked `capture` are the first choice
for starter weapons, hostile weapons, assassin armour, costumes and the backpack. The row marked
`invented` (`hsr_staff`) is not a retail observation and is not a candidate for the pack.

**cmonmeow** is strongest for pre-Searing collector and crafter stock. It carries exact reward and
trophy definitions, encoded names, modifiers and the collector that offered them. Its
`gw_presearing_items.h` also carries the six creation weapons, the Starter Sword, the Starter Bow
and the Shimmering Scale.

## Where the sources disagree

| item | disagreement | rule |
|---|---|---|
| Starter Hammer | Rurik adds `0x21F81301`, a composed attribute bonus it marks as its own. cmonmeow has the captured words without it. | Prefer the captured cmonmeow words; keep Rurik's word as a reviewed candidate, not as retail. |
| Starter Bow | cmonmeow's creation row and its Ranger quest row carry different modifier lists for the same model. | Keep both rows. The quest row is a different item context; do not merge them. |
| Caster Staff | Rurik has `caster_staff` and `hsr_staff`; the second is marked invented. | Import the captured row only. |
| Starter Shield | cmonmeow repeats the same shield in the merchant panel and in its starter-shield header. | One definition; the rows are identical. |
| File ids | Rurik writes `0x80009B60`; cmonmeow writes `39776` (`0x9B60`) for the same starter hammer. | The table keeps each source's value. The target build's capture decides the wire value when the row enters `items.json`. |

## Why `/item` only grants verified definitions

A temporary `/item` command wrote a catalogue row and sent a mid-session definition. The command
itself was not the crash: `ArenaNet.log` named missing UI textures for the imported file ids
(`0x29e` for Krytan Robes and `0x2af56` for the Starter Sword), so the items were not drawable by
this client build. The command is back as a write-only test command, and it refuses every
definition without a full live identity match.

The allowed set is the eight definitions the live client has confirmed:
`devourer_egg`, `icy_lodestone`, `unnatural_seed`, `skale_fin`, `grawl_necklace`, `worn_belt`,
`baked_husk` and `jeweled_chalice`. It writes the row and sends `CREATE_NAMED_ITEM` (`0x0161`) then
`ITEM_CHANGE_LOCATION` (`0x014B`), so the item appears without a relog. The command itself was never the
crash: the unverified item ids were.

The same crash log is the evidence that imported definitions from another build cannot be assumed
safe for this client. This is the same line `docs/03-protocol.md` draws for an unmeasured message:
the client is the judge.

The next source for ids is the running client, not another checkout. `tools/item-id-probe.py` reads
the player's bag items through Py4GW with `game_thread=False` and writes one JSON record per item:
`item_id`, `model_id`, `model_file_id`, `item_type`, quantity, interaction, identification and the
raw modifier words. The decoded `name` needs the client's game thread, so the read-only connection keeps `name_enc`, the
raw coded units, and reports the reason in `name_error`. `tools/decode-item-names.py` supplies that
thread: it feeds each `name_enc` and each generated definition's base `name` to the client's own
decoder (Py4GW's `AsyncDecodeStr` on a `game_thread=True` connection) and writes
`recordings/client/feature/items/items-live-names.json`. `tools/apply-item-names.py` writes the
decoded base names into `items.json`'s `description` fields and regenerates `items-list.md`. The GUI's
Items tab writes a timestamped file per run, and `tools/merge-item-probes.py` merges them into
`items-live-merged.json` and writes the comparison `items-verification.md`.

```powershell
python tools/item-id-probe.py --out recordings/client/feature/items/items-live-<stamp>.json
python tools/merge-item-probes.py
```

Those `model_file_id` values are the ids this client build resolves. A definition whose id is not in
that set is not safe to send to this client, whatever another emulator's capture says.

## What the live scans validated

Seven probe files, 239 distinct live item identities. Matching by the full identity
`(model_file_id, model_id, item_type)` confirms six catalogue definitions exactly:

```text
icy_lodestone, unnatural_seed, skale_fin, grawl_necklace, worn_belt, baked_husk
```

`devourer_egg` was confirmed by an earlier scan and `jeweled_chalice` was corrected from this one: the
live client's Jeweled Chalice is file `0x15db8`, model `155`, and its own name units, while the imported
definition carried model `1008` and a packed name. The name is the deciding witness - a shared file id
alone is not. The other near matches are different items, not corrections:

- `costume_body` vs "Balthazar's Doublet" (same file `0xaf6`, model `35653`);
- `starter_bow`/`ascalon_longbow` vs a live "Longbow" (same file `0x24a4`, model `137`);
- `caster_staff` vs "Holy Staff"/"PvP Holy Staff" (same file `0x1b5d1`);
- `healing_ankh` vs "PvP Healing Ankh" (same file `0x154f1`);
- `starter_spear` vs a live spear with file `0x32488`, model `1272`; its name is not resolved, so the
  imported model `18163` stays until a named live spear shows itself.

The remaining 44 definitions have no live counterpart yet. They are the starter weapons and armour,
the Krytan pieces, the costumes and several focuses/staffs/wands; the next scans are characters carrying
those, one Items-tab run each.

## What a working drop, pickup and trash send

Two captures from the live server settle what the old `ArenaNet.log` crashes never did: the crash was an
imported **item definition** whose UI texture this build lacks, not the drop messages.

`recordings/client/feature/items/items-live-20261108-173913.jsonl` (whole stacks and a trash drag) and
`items-live-20261108-174014.jsonl` (parts of stacks and equip/unequip) hold these answers:

| the client sends | the live server answers |
|---|---|
| `DROP_ITEM {item_id, count}` of the whole stack | `ITEM_REMOVE {stream, item_id}`, item `WORLD_CREATE_AGENT` (model = item id), the drop line |
| `DROP_ITEM` of part of a stack | `ITEM_UPDATE_QUANTITY {item_id, remaining}`, `ITEM_UPDATE` (`0x0162`) for the ground part with a fresh id, item agent for that id, the drop line |
| `INTERACT_ITEM {agent_id}` on a whole drop | `AGENT_PROPERTY_UPDATE_INT` 8 = 1 and 39 = agent, pickup line, `ITEM_PICKED_UP {item_id, agent_id}`, `ITEM_MOVE_TO_LOCATION`, `WORLD_REMOVE_AGENT`, property 8 = 0 |
| `INTERACT_ITEM` on a stack part | the same properties and pickup line, `ITEM_PICKED_UP`, `ITEM_UPDATE_QUANTITY` for the stack it came from, `WORLD_REMOVE_AGENT`, property 8 = 0 |
| `ITEM_DESTROY {item_id}` (trash) | `ITEM_REMOVE {stream, item_id}` |

The item agent is type 4, `h000B = 0`, `h0027 = 0x34000000`, direction `(1, 0)`, and the item's id sits
where a player agent carries its model (`items-live-20261108-173913.jsonl` seq 43). The drop and pickup
lines are a fixed four-word message prefix plus the item's own name units, committed on `Channel_Global`
(`0x005E {1, 10}`). The live server's stream field is 2; this server's load block and its new answers use
`ITEM_STREAM = 1`, which this client accepts (the same value the reference log carries).

The same capture also recorded equip and unequip: `EQUIP_ITEM {item_id}` and
`UNEQUIP_ITEM {equipped_slot, bag_id, slot}` each answer with `ITEM_CHANGE_LOCATION` and a single
`UPDATE_AGENT_VISUAL_EQUIPMENT_SLOT` (`0x006F`), and the `0x006F` slot is the **visual** one, not the
equipped-bag slot: body 2, legs 4, boots 3, gloves 5, head 6 (`items-live-20261108-174014.jsonl` seq
22-24, 40-41, 58-59, 72-73, 89-90, 101-102). Armour changes also carry energy and energy regeneration
(properties 41 and 43); those values depend on an armour model this server does not have yet, so the
equipment update is sent and the pools stay as loaded.

Ground items live in the instance, so a relog finds them where they were; a world restart does not.
`/item` remains restricted to the eight definitions whose full identity the live client has confirmed.

## Running the extraction

```powershell
python tools/extract-item-research.py
```

The tool defaults to the two checkouts in this repository and fails closed when either is absent.
It writes one JSON file and touches nothing under `crates/` or `config/`.
